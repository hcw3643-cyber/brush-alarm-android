用户不需要理解 Android 机制。执行代理应自行完成环境核对、构建和验证，向用户报告结果及必要的手机操作，不要求用户审查代码或选择实现架构。

本机没有找到 JDK/Android SDK，项目没有模型权重。因此本机未完成编译、单元测试运行、APK 生成或真机验收。所有“已实现”均指源码；不得转述成运行通过。

## 接续顺序

1. 读取原开发机项目本身的说明，检查当前分支、基线与未提交改动。保留用户原有模型、SDK 设置、签名材料和本地修改，不做 reset/clean，也不直接用整个目录覆盖。
2. 拉取 PR 分支，在适合的隔离分支或工作树中继续。若本机有额外改动，先比较并解决冲突，不覆盖本机工作。PR 不包含模型权重、私钥或编译环境。
3. 阅读 PR 与本文，核对当前检出的提交确实包含本次会话、声音/震动和恢复修改；由执行代理负责检查源码，用户无需审查 Android 机制。
4. 使用原机器已配置的 JDK 17/Android SDK 35 和合法模型文件；核对模型获取脚本要求。不要把缺少模型校验删除或把空文件伪装成模型。
5. 执行 Debug/Release 单元测试及构建。Windows 使用 `gradlew.bat`，其他系统使用 `./gradlew`，任务为 `testDebugUnitTest testReleaseUnitTest lintDebug lintRelease assembleDebug assembleRelease`。运行项目要求的相关审计，并检查发行版没有测试入口或新增日志泄漏。
6. 编译错误和测试失败由执行代理直接修复，然后再验证受影响路径；不得只把错误转给用户。保持本次需求边界，不更改模型阈值或加入跳过验证。
7. 在可用模拟器及用户指定测试手机上执行完整验收。没有设备证据的项目必须留为待验，不填“通过”。不要将真实用户手机上的强行停止/数据清除操作混入普通恢复测试。

## 必须看到实际结果的项目

| 场景 | 期望结果 |
|---|---|
| 音量为零，闹钟到点 | 有周期震动 |
| 响铃中将闹钟音量调为零 | 转为震动；调回非零恢复声音 |
| 连续点击安静一分钟 | 只接受首次，按首次截止时间复响 |
| 静音期间重建进程 | 不延长、不恢复次数，到期提醒 |
| 返回桌面、最近任务、划掉任务 | 任务不完成，继续或按允许路径恢复提醒 |
| 服务已停止后重新打开 App | 恢复提醒与验证页，不是只有验证页 |
| 熄屏但未锁定 | 到点声音/震动，不通过手动亮屏触发 |
| 锁屏且熄屏 | 到点声音/震动，验证页是否弹出单独观察 |
| 屏幕始终黑屏、全屏入口未展示 | 仍独立发出声音/震动 |
| 长时间 Doze、到点前进程不存在 | 检查正常闹钟到点提醒和实际延迟 |
| 未完成时重启，尚未首次解锁 | 恢复未完成任务；静音额度不重置 |
| 修改时区/系统时间 | 未来本地闹钟正确重排，已到期待履行不被吞掉 |
| 第59秒验证成功 | 之后不复响、不复震，页面正常结束 |
| 多个闹钟重叠 | 按队列处理，旧结果不能完成新会话 |
| 某次服务启动失败 | 本次可恢复，下一次正常闹钟仍有系统登记 |
| 所有任务验证完成后 | 等待至少两个恢复周期，无提醒复活 |

普通进程死亡测试要确认 PID 确实变化；`am kill` 可能没有杀掉前台进程。Task Manager Stop 与设置中的 Force Stop 必须分别记录，后者不是普通应用可保证自行恢复的场景。

记录计划时刻、广播到达、前台服务启动、播放/震动请求及实际听到/感觉到提醒的时刻。不能把日志里的“请求成功”替代真实声音/震感确认。诊断不采集刷牙视频、面部图像或上传隐私资料。
